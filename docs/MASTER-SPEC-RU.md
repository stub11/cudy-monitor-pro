# Cudy Monitor Pro — мастер-ТЗ для автономной разработки
Версия ТЗ: 1.0, 2026-11-08. Статус: принято как рабочее ТЗ на основе утверждённого пользователем макета.

## 0. Назначение и запреты
Доработать СУЩЕСТВУЮЩИЙ репозиторий stub11/cudy-monitor-pro и Rust/web-приложение в source/cudy-monitor, не создавать демопроект.
Пользовательский эталон — 8237.png, 1536x1024, SHA-256 89d5701f72b24358a9d26574c7e2db99f0b45cf29a7905362b7540732180331a.
Исходные файлы и сборочные временные данные — только D:\AI и U:\AI work на ПК. Не изменять рабочую конфигурацию роутера без отдельной необходимости. Не публиковать приватные данные.
Всё из макета должно быть реализовано на реальных данных или явно показано как 'недоступно'; имитация показателей запрещена.

## 1. Визуальная система
1.1. Desktop: тёмно-синий фон, фиксированная/липкая левая колонка, контентная сетка с мягкими границами, карточки с радиусом 12–18px, небольшими тенями, внятные отступы. Голубые/синие акценты действий, фиолетовый CPU-график, зелёная память, оранжевая температура. Значения и состояния различаются не только цветом.
1.2. Desktop с ширины ~1280: 5 информативных карточек верхнего ряда (CPU, температуры, RAM, накопитель Entware, uptime), ниже графики и сводки; адаптировать компоновку, не фиксировать пиксельные размеры. На больших экранах контент не растягивать бессмысленно.
1.3. Tablet 768–1199: боковая навигация сворачивается, карточки перестраиваются в 2–3 колонки. Mobile 360–767: однотипная навигация через меню, компактные метрики в 2 колонки при наличии места, остальные секции вертикально. Touch-цели от 44px, отсутствие горизонтального скролла страницы.
1.4. Типографика: системный sans-serif без внешних CDN; устойчивые табличные цифры и единицы, контраст WCAG AA для текста, фокус клавиатуры виден. Знаки температур, скорости и объёма точные.
1.5. Палитра, типографика, интервалы, высоты и состояния элементов должны быть оформлены как CSS custom properties, не копироваться разрозненно. Для неактивного состояния, загрузки, отсутствующих датчиков и сетевых ошибок предусмотреть единые компоненты.
1.6. Верх: название 'Обзор системы', модель, связь с бэкендом, интервал обновления, локальная дата/время, настройка. Не выдавать фиктивные статусы 'работает стабильно'.
1.7. Графики используют стабилизированные оси и сохраняют размер при смене значений; обновлять данные без полного перерендера страницы. Уважать prefers-reduced-motion; не мигать и не дёргать интерфейс при опросе каждые 2 секунды.
1.8. Сверять реальный HTML в браузере со всеми блоками утверждённого макета: иерархия, стиль, карточки, меню, мобильная версия. Макет — направление визуала; техническая корректность и доступность имеют приоритет над декоративными эффектами.

## 2. Разделы и функциональная спецификация
2.1. ОБЗОР: CPU загрузка%, частота МГц при доступности, число ядер, 1/5/15 load averages; температуры с указанием источника; RAM used/total, cache, buffers; Entware filesystem used/free/total с путём монтирования; uptime и, если подтверждено расписанием, время следующей перезагрузки; 5-минутная история CPU/RAM/температуры; per-core диаграммы; сеть по выбранному интерфейсу, Rx/Tx, пики только из реально измеренных данных; процессы-потребители памяти с категорией; датчики. 'Пик' не путать с текущей скоростью, uptime не путать с boot-time.
2.2. ПРОЦЕССЫ: список PID, имя, реальная командная строка с безопасной обрезкой/редакцией, CPU%, RSS MiB, статус, группировка только если обоснована; сортировки по CPU/памяти/имени и поиск; обновление таблицы без потери выбранной сортировки и прокрутки. Нет функций уничтожения процессов без отдельного проектирования безопасного управления.
2.3. СЕРВИСЫ: обнаруживать реально существующие службы (например D2K/DoQ/KeenKit/собственный монитор, где доступны); состояния running/stopped/unknown/unsupported; разделять процессы, opkg и системные init/procd службы. Если разрешены действия — start/stop/restart лишь по явному нажатию, подтверждение для разрывов сети, проверка успешности, таймаут, понятная ошибка и отказ от опасного shell injection. Не показывать активные кнопки управления для неизвестных служб. Монитор не должен останавливать себя посреди запроса без специально продуманного механизма.
2.4. СЕТЬ: динамическое обнаружение WAN/LAN/Wi-Fi без жестко прошитых br-lan, wan, wlan0; RX/TX и история, адреса/маски/шлюзы/DNS при доступности, тип подключения; DHCP-клиентов считать только при наличии надёжного источника. Не путать активные TCP-соединения с conntrack. Графики не должны показывать скорость 'пик' из других интерфейсов.
2.5. ХРАНИЛИЩЕ: физические USB/флеш/разделы и mounts, sizes, свободно, read-only, файловые системы, Entware, top usage только безопасным ограниченным сканированием. Отсутствие USB — нормальное состояние.
2.6. ЖУРНАЛЫ: чтение доступных локальных журналов без бесконечного накопления; диапазон/фильтрация по уровню и тексту, предел строк и размеров, маскирование токенов и адресов при экспорте. Не показывать секреты из аргументов процессов и файлов конфигурации.
2.7. НАСТРОЙКИ: тема (тёмная по умолчанию), частота обновления, единицы, диагностика, версия, безопасное обновление/откат согласно существующим механизмам. Сохранение параметров не должно менять сеть и DNS; настройки только для интерфейса и самого монитора.
2.8. Во всех разделах: пустые состояния, skeleton/загрузка без скачков, lost connection/retry, API errors, пояснения 'не поддерживается' без падения.

## 3. Данные и архитектура
3.1. Сохранить Rust-бэкенд, встроенный web UI, минимальный RAM/CPU, без обязательных Python/Node на роутере, CDN, облака или аккаунтов.
3.2. Каждый показатель снабжать typed value, unit, source, timestamp, availability. Backend не должен подменять отсутствующие данные нулями; фронтенд должен различать 0, null, unavailable и stale.
3.3. Протокол JSON API версионировать, тестировать ошибки/пропущенные поля. Инструменты опроса — ограниченные по времени, чтение /proc, /sys, /etc, а внешние программы — только если они существуют и безопасны.
3.4. Использовать разницу счётчиков / время для скорости и CPU, защищаться от reset/wrap/первого измерения. Не показывать ложные 100% CPU или гигантские скорости при restart.
3.5. 2-секундный опрос по умолчанию в открытой вкладке; пауза/редкое обновление для скрытой вкладки; запросы не накладывать; недоступность отмечать после таймаута; не создавать быстрорастущие логи/файлы на флешке.
3.6. Безопасность: доступ локально по умолчанию, ограничение bind/interface; открытие в LAN — только осознанное. Панель сегодня без пароля: никакого WAN exposure; команды сервиса по сети требуют отдельной проверки угроз/CSRF/аутентификации, до этого опасные действия должны оставаться отключёнными или строго ограниченными.
3.7. Модель/прошивку/архитектуру определять из устройства. Учитывать KeeneticOS/Entware и OpenWrt/Entware; Netis N6 v2/NX32U — целевые кандидаты, но НЕ объявлять аппаратно проверенными до тестов. Нестандартный LAN, несколько адресов, VPN, VLAN, multi-WAN должны иметь предсказуемое обнаружение и явный выбор в неоднозначных случаях.
3.8. Установщик и IPK должны оставаться совместимыми: ARM64 Entware, --check, --lan, --local, --bind-ip, сохранение пользовательских настроек, безопасное обновление с хешами, rollback, stop/start без потери доступа к роутеру.

## 4. Технический инструментарий на ПК
4.1. Desktop Commander для удалённого Windows, GitHub connector для коммитов/CI/релизов; Git, Node.js, Python уже обнаружены.
4.2. Проверить установленный Rust toolchain; если отсутствует — установить только под D:\AI\tools и настроить CARGO_HOME/RUSTUP_HOME/CARGO_TARGET_DIR/TEMP/TMP, не размещая новые данные в C:\. Предварительно обследовать существующие toolchains и кэши.
4.3. Для визуального тестирования использовать Playwright + Chromium или аналог, при необходимости браузерные бинарники/кэши в D:\AI. Допустим Figma для последующей детализации, но утверждённый PNG — главный источник правды.
4.4. Тестировать при 1536×1024, 1280×800, 768×1024, 390×844, 360×800, light/dark системных настройках (при сохранении тёмного интерфейса), 100/125/150% scaling; с mock API для ошибок и графиков. Делать скриншоты проверяемых версий и отчёт о различиях.
4.5. Не подключать сторонние плагины, которым требуются доступы к SSH или GitHub, если существующих Desktop Commander и GitHub достаточно.

## 5. Приёмка и релиз
A. Визуальное сравнение с эталоном, реальная мобильная адаптация и доступность без обрезки, управление с клавиатуры.
B. Все разделы работают на реальных данных или показывают явную недоступность.
C. 10 минут обновлений каждые 2 секунды без прыжков сетки, потери сортировки, утечек памяти, тяжёлых операций на роутере.
D. Тесты unit/integration/installer: фикстуры OpenWrt, KeeneticOS, неизвестный роутер, отсутствующий sensor, один/несколько LAN, неизвестная служба, пропавшая сеть, инкременты/сбросы counters.
E. Smoke-test IPK в чистой среде, upgrade+rollback, проверка SHA-256 и сохранения настроек, без изменения DNS/маршрутизации.
F. Проверка безопасности перед публикацией: scan secrets, приватные IP/реальные адреса, журналы, реальные ключи, токены, пароли; очистка графических снимков.
G. Честный статус: CI PASS не означает реальный тест на Netis/OpenWrt. Аппаратные проверки отмечать отдельно.
H. Коммитить этапами, поддерживать CHANGELOG и README, именовать релизы однозначно; не считать готовым до скриншотов, тестов и сверки.
